# レビューしてほしい点

外部レビュー用。**実装者（Claude）が自覚している弱点と判断の分かれ目**を先に挙げる。
ここに書いていない問題こそ見つけてほしいが、まずここから見てもらうと時間が無駄にならない。

前提として、仕様は [`docs/spec.md`](spec.md)。現状は **Supabase 未接続**で、
記憶域はすべてメモリ実装（`src/flow/memory-store.ts`）。**プロセスが落ちると全部消える。**

## 1. 同時予約の直列化（未実装・設計だけ）

**優先度：高。** まだ DB 実装が無いので、コードではなく設計を見てほしい。

仕様に当初こう書いていたが、これでは防げないと判断して書き直した（spec §6「同時予約」）。

```sql
-- 誤り：for update は「読めた行」しか施錠しない
select count(*) from bookings where slot_id=$1 and booked_date=$2 ... for update;
```

枠が空（該当行ゼロ）だと施錠する対象が無く、2つのトランザクションが同時に
0 を読んで両方 insert する。既存予約が1件でもあれば偶然直列化されるため、
**空の枠でだけ壊れる。**

いまは親の `slots` 行を `for update` して直列化する設計にしている。
他の手（advisory lock / serializable + リトライ / 排他制約）と比べて妥当か。

## 2. 200即返し後の非同期処理（`src/webhook/app.ts`）

LINE に 200 を返してから `void handleEvent(...)` で処理する。reply token の
寿命が短いため待たせられない、という理由（spec §4）。

**プロセスがその間に落ちるとイベントは失われ、再送もされない。**
Fly のマシンは `auto_stop_machines = "suspend"` で停止しうる。

キューを挟むべきか、この規模（1施設・1日数件）なら許容か。

## 3. 冪等の粒度（`src/db.ts` / `src/webhook/app.ts`）

`webhook_events` への insert を**処理の前**に行い、一意制約違反で重複を弾く。
つまり **at-most-once**。処理が失敗しても event_id は消費済みで、再送は無視される。

「先に SELECT して無ければ INSERT」だと同時到着で両方通るため insert で判定
しているが、成功後にマークする方式（at-least-once + 冪等な処理）の方が
良いかもしれない。二重送信と取りこぼしのどちらを取るか。

## 4. reply token の単一使用（`src/flow/machine.ts`）

reply token は1回限り。2回 reply すると2回目が 400 で落ち、こちらは 4xx を
再送しない設計なので**利用者には片方しか届かない**。

実際に埋め込んでいたバグで、枠が埋まっていた場合に「埋まりました」だけ届いて
選択肢が出ない状態だった。いまは `prefix` で1回にまとめ、呼び出し回数を
数えるテストを置いている（`tests/flow.test.ts`）。**同種の見落としが他に無いか。**

## 5. LINE API エラー時の再送（`src/line/client.ts`）

spec §12 は「リトライ1回」。**4xx では再送しない**と解釈した。要求自体が悪いので
繰り返しても直らず、実際には成功していた場合に二重送信する危険だけが残るため。
再送するのは通信エラーと 5xx のみ。この解釈で妥当か。

## 6. 管理画面の認証（`src/admin/api.ts`）

共有トークン1本（`ADMIN_TOKEN`）をヘッダで送るだけ。仕様に認証の記載が無いが、
公開URLに予約者の氏名が出るため最小限を入れた。**トークン未設定ならルート自体を
生やさない。** 複数人で使うなら不十分。どこまで必要か。

## 7. タイムゾーンの扱い（`src/slots/time.ts`）

外部ライブラリを使わず `Intl.DateTimeFormat` でオフセットを引いている。
DST 境界で1回では収束しないため2回引き直している。Asia/Tokyo に DST は無いが、
TZ を設定値で持つ以上は壊れないようにしたつもり。**この実装で漏れが無いか。**

## 8. 締切の境界（`src/slots/availability.ts`）

「前日18:00」を、**18:00 ちょうどは締切済み**として扱っている（spec §6 の当初の
式が等号で除外していたため）。テストで1ミリ秒前と直後の両側を押さえている。
運用上これで良いか。
